# The chat gets an optional, grounded, swappable AI layer on top of the rule-based chat

Status: accepted

The chat has no language model today (ADR 0001, ADR 0002). We now add one, using free or locally run models only, to make the chat feel like a chatbot: it understands looser phrasing, follows up on the previous question, and explains in its own words. The rule-based chat stays underneath as the path that always works.

## Decisions

1. **Numbers and places still come from code (ADR 0001 is unchanged).** The model never writes a count, a place name, a date or a source. It may choose a structured intent that code then validates, and it may write the wording of an explanation.
2. **Rules first, model second.** A question is understood by the rules as today. The model is called only when the rules cannot understand the question, or when a follow-up needs the earlier turns. In the first case it returns a structured intent (JSON) that code validates against the known places, windows and filters; an invalid result is treated as "not understood". In the second it rewrites the follow-up as a standalone question, which then goes through the rules like any other. This also keeps free quota for the questions that need it.
3. **Explanations are grounded.** The model may answer an explanation question only from the passages that retrieval returned, and must name the passages it used. Code checks that the passages it names include the best retrieved one (a number that names no passage is ignored: small models often add one too many, and the source shown never comes from the model), that its text brings in no number or place the passages lack, and that it is of a sensible length. If a check fails, or the model says it cannot answer, the reply is the verbatim quotation as before. The quotation and its source line are always shown under a model-written answer.
4. **Health and field-action documents are never paraphrased.** A document can be marked as quote-only in its front matter; the smoke and health documents and the field-action document are. Their sources differ in detail (WHO advises an FFP2/N95 mask, Kemenkes does not for children and pregnant women), and a small rewording can change the meaning.
5. **Retrieval becomes hybrid.** PostgreSQL full-text search stays and goes first, and a search by the meaning of each passage's heading is added after it, for the questions the words alone miss. The embedding model runs inside the API container (a small multilingual model through ONNX, baked into the image), so it costs nothing, sends no text away, and works even when the chat model is down. The vectors are stored as a plain array column and compared in the application: pgvector was the first plan, but for a few dozen passages it is not needed (see below). A heading must be at least 0.85 similar to the question to be offered, which the evaluation in `backend/tests/test_knowledge_eval.py` supports: fitting paraphrases scored 0.85 to 0.96 and the closest question the documents do not answer scored 0.80. If the embedding model is unavailable, search is by words only. This replaces the "full-text search only, no embedding model" part of ADR 0002.
6. **One model interface, chosen by configuration.** The backend talks to the model through one OpenAI-compatible chat client. The address, model name and key come from `.env`, so a local model (Ollama, llama.cpp) and a hosted free API (Groq, OpenRouter, Cloudflare Workers AI) are interchangeable without a code change. With no address configured the AI layer is off and the chat behaves exactly as it does today.
7. **Simple mode is the fallback.** There is a global limit on model calls per minute and per day, and a cache of model-written answers. When the model is down, slow, rate limited or over budget, the chat falls back to the rule-based path and the panel says it is in simple mode. A reply never fails only because the model did.
8. **User text is data, never instructions.** The system prompt is fixed, user text is passed as delimited data, the model has no tools, and everything it returns is validated by code before it is used. The chat stays within the sources: short greetings get a friendly reply, everything else outside the sources is turned away as today.
9. **Privacy.** Question text may go to a hosted provider, so the panel carries a permanent note that questions are processed by an AI service and should hold no personal data. Only public data is sent to the model. Questions are not logged or stored. When two providers are otherwise equal, the one that does not train on prompts is preferred.
10. **Conversation memory lives in the browser.** The browser sends the last few turns with each question; the server stays stateless and stores nothing.
11. **Tests do not need a model.** Automatic tests use a fake model client so they stay deterministic, offline and free, and cover every guard above. The quality of a real model is checked by a separate, manual evaluation script that is not part of CI, and the local model is chosen with it.

## Considered options

- **Model writes everything, including numbers (plain RAG over the database).** Rejected for the reason in ADR 0001: a misquoted or rounded figure is worse than no answer.
- **Model as router only, answers stay templates and quotations.** Rejected as too small a step: the chat would not feel like a chatbot and could not follow up.
- **Hosted free API only, or local model only.** Rejected as a fixed choice. Free hosted limits are per application, not per user (for example Groq's free tier allows roughly a handful of chats per minute for the whole app), change often, and some providers train on free-tier prompts. A local model needs a host with enough memory (the only free host found that can run one is an Oracle Cloud ARM VM, which needs a card for sign-up and gives about 3 to 6 tokens per second for a 3B model by estimate). Which one production uses is decided when hosting is done, and the single interface keeps both open.
- **Embeddings from a hosted API.** Rejected: it would make retrieval depend on a provider and send text out for no gain at this size.

## Consequences

- **pgvector was dropped for now.** The PostGIS image the project uses (`postgis/postgis:16-3.4`) is built on Debian 11, whose PostgreSQL package repository no longer serves pgvector, and the newer PostGIS images would force every existing database to upgrade its PostGIS extension. For about thirty passages a comparison in the application is instant. If the knowledge base ever grows to thousands of passages, the array column can move to pgvector behind the same function, with a database image change decided then.
- The threshold of 0.85 has a thin margin (0.80 against 0.85) and was set from about seventy questions of our own. A fitting paraphrase scoring 0.82 is turned away rather than answered; that is the intended direction of the error. Retune it with the evaluation, never by feel.
- Only the headings are embedded, not the passage text: the full text scored worse at telling answerable from unanswerable questions, and the model reads only the first part of a long text anyway.
- The API image grows by the embedding model and its runtime.
- ADR 0002 is partly superseded: its full-text-only retrieval and its "never rephrase" rule no longer hold, except for quote-only documents. The rest of it (reviewed documents with a source and a review date, the "not in our sources" answer, loud failure on a malformed document) still holds.
- Model quality in Indonesian and the speed of a small local model are not yet measured; the evaluation script exists to measure them before a model is chosen.
- Free-tier limits and data policies change; they must be re-checked in the provider's console when one is picked.
